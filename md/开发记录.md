### 1. 单因子测试接入特征面板缓存 + 分位聚合向量化（v1.18.69 → **v1.19.0**）
- **背景**：用户报「以前算一个市值因子只要 10 秒，现在 24-32 秒」+「固定 K 档只选 1 个和全选耗时差不多」。两步都是**先剖析再动手**。

### 6. 面板求值内存加固（v1.18.1，本轮提交）
- **背景**：多公式 × 并行 × 缓存驻留三条放大链叠加（共用 evaluator 节点缓存跨公式线性累积 × ×12 worker × 每 worker 768MB bin LRU），用户全 A 极端压测（6 公式含 CUP_POOL 24.6 万字符）后期内存 90%+ 被系统清理；终因是 CUP_POOL 单树数千节点 × 每节点 ~MB 单 worker 也被撑爆。
- **四招**（panel_expr）：
  ① 节点缓存 **LRU 封顶 512MB/worker**（`_node_cache` 改 OrderedDict + Series 字节记账，写满 popitem 最旧；`QLIB_SFT_PANEL_NODE_CACHE_MB` 可调）；
  ② `eval_expr` **按表达式清空**节点缓存（防 N 公式 × 全树累积，数值零影响）；
  ③ 并行 worker **内存自适应**：CPU 维度 ∩ 内存维度（avail ÷ `QLIB_SFT_PANEL_MEM_PER_JOB_GB` 默认 3GB），可用 <`QLIB_SFT_PANEL_LOW_MEM_GB` 默认 6GB 再收敛 ≤avail/2；`QLIB_SFT_PANEL_JOBS` 显式覆盖；
  ④ 每 worker 盘缓存预算 = avail×40% ÷ n_jobs（64~768MB，`set_bin_cache_mb()` 注入 `_worker_init`；显式 `QLIB_PANEL_BIN_CACHE_MB` 优先）。
- **实测**：CUP_POOL 120 只两年单进程峰值 **722MB**（封顶前数 GB）；2000 只 × 5 公式并行峰值 RSS 合计 **2.25GB**（旧估 >6GB）；41 回归全绿；版本 1.18.0→1.18.1。

### 7. 速度回退咨询实测结论（9/10 归档）
- 用户问"这一通操作后速度慢多少"。同口径 profile（CWH_BREAK_WAIT20_F1 4 万字符 × 300 只 × 2024-25）：**原始 20.54s → +binLRU 7.46 → 9/9 深夜 4.17/2.68 → 当前全改动 6.50/3.45(warm)**。求值无回退且比最初快 3~6×；当前与深夜快照的 2.3s 差为同函数调用数下的环境噪声。
- 真正的"慢一半"感知来源：本机 32GB 可用仅 ~17.5GB → 全 A 并行 worker 从 CPU 允许 12 被内存维度压到 **5**（≈2.4× 并发差）；这是护栏换稳定，可用 `QLIB_SFT_PANEL_JOBS`/`QLIB_SFT_PANEL_MEM_PER_JOB_GB` 放宽。

### 1. BarData 抽象化：禁止裸实例化（采纳同事 issue）

- **背景**：`BarData` 是可被直接实例化的普通 Pydantic 模型，但业务上只应使用子类 `DailyBar`/`MinuteBar`：二者字段与 `BarData` 完全同构，反序列化/下游无法区分日线与"裸 K 线"；`datetime` 语义（日线=当日、分钟=K线结束时刻）只能靠注释，类型层无法强制。
- **改动**（`backend/app/datasource/base.py`）：`BarData` 新增抽象只读属性 `bar_kind`（`@property @abc.abstractmethod`），`DailyBar`/`MinuteBar` 分别返回 `"daily"`/`"minute"`。此后 `BarData(...)` 直接抛 `TypeError: Can't instantiate abstract class`。
- **要点**：pydantic v2 的 `ModelMetaclass` 已继承 `ABCMeta`，无需显式继承 `abc.ABC`；抽象成员是属性而非 Pydantic 字段（字段无法标 abstract），不参与序列化，JSON 契约不变（实测 `model_dump_json()` 不含 `bar_kind`）。
- **验证**：qlib 环境（pydantic 2.13.4）实测——裸 `BarData` 拦截生效、`DailyBar`/`MinuteBar` 构造与序列化正常、`qlib_source`/`rqalpha_source` 导入正常。
- **局限**：ABC 只解决"防裸实例化"；若将来需按 JSON 判别日线/分钟线，需引入 Pydantic discriminated union（会改 JSON 契约），另议。

- **问题**：qlib bin 区间内"每日一行、停牌日 NaN"。官方 dump_bin 也是 `reindex(日历)` 补 NaN；官方 Rolling 是 `min_periods=1`+skipna（不剔行）。但益盟/聚宽数据没有停牌行 → 复牌首日 `Ref(close,1)=NaN`（官方/我们都是），窗口被停牌段截断 → 与益盟不一致，A158 的 Ref/窗口因子与官方基准在停牌段也失真。
- **方案**：新增外挂算子 `SR(X[,M])`（ops_ext.py）：按停牌掩码剔 NaN 行 → 返回连续交易日序列（后续 qlib 内建 Ref/窗口/算术自然按删行语义）；读取向前扩展 250 个交易日跨停牌段（复牌首日能取到停牌前收盘）；`SR($factor,$close)` 按 $close 掩码删行（factor 停牌日仍有值，必须显式掩码，否则与价格字段组合会把停牌行外对齐回来）。
- **接入**：`CachedQlibDataLoader` 默认对 feature 组表达式统一包 SR（`strip_suspended=True`），label 不包 → 多因子 A158/360/公式/mixed 全部统一；单因子测试只对因子表达式包 SR，涨停/停牌判定元数据（CLOSE/CHANGE/T1_*）保持原始含 NaN（否则剔除逻辑失效）。
- **验证**：万科 2016 停牌半年复牌首日 `Ref(close,1)` NaN→35.514（停牌前收盘）、`Mean(close,3)` 连续；公式 `RET:CLOSE/REF(CLOSE,1)-1` 复牌日=-0.0999。A158 的窗口因子（IMAX/MA/ROC 等）同样受益。
- **⚠️ 语义变更**：此后训练特征 = 删停牌行语义，**所有历史训练/回测结果不可直接复现，需重跑**。SR 扩展读取 250 个交易日会略微增加特征计算读取范围（磁盘缓存 key 已含包装后表达式，自动刷新缓存）。

### 9. 并发显示即时反馈（提交/结束时立即刷新）

- **需求**：点"开始测试"后并发显示应立即 +1（服务器多用户场景下，轮询 3 秒间隔太慢）；任务结束/失败/取消后要立即 -1，避免"假占用一直挂着"的尴尬。
- **澄清**：并发控制由后端信号量保证，显示不及时也不会"爆"（会正确排队）；本改动只提升反馈即时性。
- **实现**（`App.tsx` + `SingleFactorTestPanel.tsx`）：
  - `App.tsx` 新增 `refreshCapacity()`（立即 GET `/api/backtest/capacity` 更新显示），作为 `onCapacityChange` prop 传给单因子面板；
  - 单因子面板：提交成功 200ms 后触发刷新（等后端线程登记占用/排队）；轮询到终态（success/failed/cancelled/404）时触发刷新（后端已归还配额，显示 -1）；

### 11. 历史回测列表刷新 + 并发回测 "Run not found" 修复

- **问题**：
  1. 提交多个回测后，历史列表只显示最新一个，其余要点"刷新"按钮才出现；
  2. 多任务并发/复用参数回测报 `Run with id=xxx not found`（任务状态显示"失败"）。
- **根因**：
  1. 前端 `App.tsx`：提交回测后不刷新历史；且轮询里 success 分支的 `break` 导致同一轮多个任务同时完成时只刷一次，其余任务的刷新被跳过；
  2. 后端 `qlib_parallel.py`：qlib 的 `MLflowRecorder.end_run` 用 `mlflow.end_run()`（依赖 mlflow **全局** active run 栈），多线程并发时各线程 run 互相覆盖，结束时会取到别的线程的 run_id 去 set_terminated → 在独立 db 里找不到 → `MlflowException: Run with id=... not found`（在 `with R.start(...)` 退出时抛，回测失败）。
- **修复**：
  - `App.tsx`：提交回测后立即 `setHistoryRefreshKey(+1)`；轮询改用 `anyDone` 标志统一刷新（不再因 break 漏刷）；
  - `qlib_parallel.py`：patch `MLflowRecorder.end_run`，改用 recorder 自身的 `client`（线程独立 sqlite uri）+ `id`（本线程 run_id）直接 `set_terminated`，不依赖 mlflow 全局状态；失败时回退原实现。
- **重要坑（补充）**：补丁首次实现里 `from qlib.utils import TimeInspector` 抛 `ImportError`（正确路径是 `qlib.log.TimeInspector`），且 `task_manager._execute` 里补丁调用被 `except Exception: pass` 吞掉 → **end_run 补丁从未生效**（R 线程隔离生效、end_run patch 静默失败），并发/取消回测仍报 `Run not found`。已修正 import 并用脚本验证 `MLflowRecorder.end_run` 确实被替换。**教训：外挂补丁被 try/except 吞异常时极难发现，验证补丁是否真正生效要用脚本检查被 patch 对象的属性/函数名。**
- **再补一坑**：patch 绕过 `mlflow.end_run` 后，mlflow 的（线程本地）active run 栈里被 `start_run` push 的 run **不再被 pop** → 同一线程下一次 `start_run` 报 `Run with UUID ... is already active`。修复：patch 版 `_end_run` 在 `client.set_terminated` 成功后，手动按 `run_id` 从 `fluent._active_run_stack.get()` 中移除本 run。
- **验证**：3 个回测并发 + 中途取消 1 个：其余 `success`、取消的 `cancelled`，无 `Run not found` / `already active`。

### 12. ⚠️ 重要坑：8/26 的旧模型在当前环境不可复现（数据/环境漂移，不是 BUG，但"要命"）

- **现象**：用户拿 8/28 的历史回测参数（加载模型 `8eaa390fe440`）改了个滑点重新提交，结果年化从 47% 掉到 18.6%，初看以为是"千二滑点太可怕"。
- **最终排查结论（经过逐项实证，勿再踩）**：
  1. **滑点 `impact_cost` 在这套参数下几乎不生效**：qlib 冲击成本公式为 `adj_cost_ratio = impact_cost × (本单成交额 / 当日该股总成交额)²`，topk=50 分散持仓下单笔订单占个股日成交额比例极小，平方后趋近 0；实测 4 个任务成本率全部相同（0.0897%），改 `impact_cost` 不产生额外成本。
  2. **训练 label 从未改变**：`74dbf51`（8/31 16:37）曾短暂改成 `Ref($close,-(n+1))/$close-1`（T 起算），80 分钟后 `f0c6e2f`（17:53）又改回 `Ref($close,-(n+1))/Ref($close,-1)-1`（T+1 起算，与单因子/回测 shift=1 对齐）。**当前三处（handler.py / single_test.py / analysis.py）与 8/26 训练时全部是 T+1 起算。**
  3. **不是 handler 管道差异（推翻初判）**：用 8/26 版 handler（继承原生 Alpha158 + QlibDataLoader）在当前环境训练，结果与当前代码训练**完全一致**（预测相关 1.0），都复现不了 8/26 的模型。
  4. **不是随机种子**：当前环境两次独立训练预测相关 1.0（完全确定）。
  5. **不是特征缓存 bug**：`CachedQlibDataLoader` 缓存特征与 `D.features` 直接计算完全一致（max diff = 0）。
  6. **实测差异**：8/26 模型（A）与当前重训模型（B/C）在相同特征输入下预测 Spearman 相关仅 **0.50**，top50 重合约 70%，回测持仓重合率 41%。
  7. **最终排查：数据其实没变（更正）**：`data/cn_data/features` 目录 mtime 8/31 17:37 是**新增 `market_cap.day.bin` 字段**造成的假象（新增文件会更新目录 mtime）；**行情 .bin（open/high/low/close/volume/factor 等）全部仍是 8/22 08:00，从未重 dump，复权因子 factor 也没变**。环境（qlib 无改动、pandas/numpy/scipy/xgboost 均 8/24 安装）也未变。
  8. **A≠B 的根因最终未定论（诚实记录）**：代码、数据、label、参数、环境、缓存全部核对一致，当前环境也无法复现 A。最可能是 **8/26 训练 A 那一刻后端运行的代码/数据存在一个已无法考证的中间状态**（当时未提交的本地改动，或数据的一个短暂状态），git 与文件系统均无记录。
- **教训**：
  - **"相同参数重新训练"≠"复现历史模型"**——训练数据/环境漂移会让新旧模型不可比（即使代码、label、特征表达式、超参全一样）。对比回测参数（滑点、成交价、手续费）时必须**加载同一个模型**（`load_model_task_id`）才能控制变量。
  - 8/26 模型的 47-48% 是**真实的回测成绩**（8/28 与 9/1 两次独立回测 100% 重合验证），但它是历史产物，当前环境重训已无法复现。
  - **可复现性缺口**：项目目前没有"训练签名"（代码 commit + 数据 dump 时间戳 + 依赖版本 + 关键参数哈希），一旦训练时刻的状态漂移，历史模型就不可复现。若需严格复现，应引入训练快照。
- **对比滑点影响的正确姿势**：加载同一模型（如 `0e8ba7a5890c` 的段模型），仅改 `impact_cost`，提交两个对照回测。

### 13. 复权方式选项（不复权/前复权/后复权）+ 训练签名快照（MD5）

- **背景**：当前全链路（训练/回测/单因子测试）用的都是**原始价（未复权）**——qlib `FileFeatureStorage` 直接读 `close.day.bin` 原始值，项目也没做过复权。原始价在除权日有跳空，收益/特征会失真。为满足"训练用复权价"的需求，加了复权选项；同时因 #12 暴露的"历史模型不可复现"问题，加了训练签名快照。
- **实现（全部在项目代码层，未碰 qlib 内核）**：
  - 新模块 `backend/app/engine/adjust.py`：`adjust_expr()` 把表达式里的 `$close/$open/$high/$low/$vwap` 替换为 `($close*$factor)` 等复权表达式；前复权在回测 quote 层额外除以区间最新因子归一化。
  - 特征/label 复权：`handler.py` 三个 handler（SelectedAlpha158/360/FormulaHandler）新增 `price_adjust` 参数，`get_feature_config/get_label_config` 返回前对表达式复权。
  - 回测成交价复权：`board_exchange.py` 的 `BoardAwareExchange` 新增 `price_adjust`，`get_quote_from_qlib` 加载行情后对价格列按 factor 复权（前复权再除以每只股票最新因子）；涨跌停判断用 `$change`（复权无关）+ 复权后的 `$close` 反推昨收，同比例缩放判定等价，不受影响。
  - 单因子测试复权：`single_test.py` 的 label/因子/价格字段同样走 `adjust_expr`。
  - 参数：`BacktestRequest` / `SingleFactorTestRequest` 新增 `price_adjust`（默认 `none`，老任务复用自动为不复权）。
  - 前端：回测表单与单因子面板新增"复权方式"下拉框（不复权/前复权/后复权）；**复用老回测参数时强制 `price_adjust='none'`**；**复用模型权重时若复权方式与源不一致，自动改新训练**（复权改变特征分布，旧权重不匹配）。
- **重要事实**：对**比率类**特征（MA/ROC/RSV）与收益（label/净值），**前复权与后复权数学等价**（整体差常数因子，分子分母同时缩放抵消），训练结果完全相同；区别只在价格绝对值（前复权贴近实盘价）。三选项的实质区别是"复权 vs 不复权"。
- **训练签名快照**：`artifacts.py` 新增 `_save_train_signature()`，每次回测在产物目录生成 `train_signature.json`，记录 git commit、数据版本（features 目录 mtime）、依赖版本（xgboost/pandas/...）、`price_adjust`、特征指纹 MD5、参数 MD5。用于历史模型追溯与复现定位。
- **验证**：复权表达式可在 qlib 计算；原始/复权 label 数值不同（95% 样本、最大差 0.056）；提交 `price_adjust=backward` 回测成功跑通；`train_signature.json` 生成正常。后端已重启（v1.4.9），前端热更新生效。

### 14. ⚠️ 重大发现：周滚动回测"只买不卖"结构 BUG（收益虚高 45%~254%）

- **问题**：排查 `20260831-230547_LightGBM_all_2019_2026_5889678cb400`（topk=20、周滚动 test_win=1week、持有期 5 天）年化 45% 时发现：**全年 7850 笔调仓全是买入、0 笔卖出**；且成交额差异巨大（目标金额都是等权 ~398 万/只，但实际几万~几百万不等）。用户怀疑"未来函数/调仓 BUG 导致结果虚高"。
- **根因（三层）**：
  1. **qlib 账户纯现金起步**：`backtest_daily` 的 `account` 传 float 时官方注释即 "Using Account with only initial cash"（只有现金、无初始持仓）。
  2. **滚动回测每段独立重建账户、持仓不跨段**：`qlib_engine._run_rolling` 每段用 `PortAnaRecord(account=carry_account)` 独立跑，`carry_account` 只把上段总资产作为新现金，**上段持仓不传给下段** → 段末持仓被"免费清仓"。
  3. **策略段首调仓从空账户取持仓 → 无仓可卖**：`PeriodicTopKStrategy.generate_trade_decision` 段首 `current_stock_list = 空`，卖出循环空转，只生成买单。
  - **触发条件**：段长 ≤ 持有期。`test_win=1week`（5 交易日）= `n_days_hold=5` → 每段只调仓一次（段首），账户为空 → 只买不卖。扫描全部历史回测验证：**所有周滚动任务均 0 卖出 + 年化虚高（45%/213%/254%）；月/季/半年滚动段长 > 持有期，段内多次调仓，正常买卖（年化 -34%~+12.6%）**。
- **收益虚高机制**：每周换仓跳过卖出成本（close_cost 0.15% + 卖出滑点 0.2%），一年约 52 次 ≈ 省 15-18% 换手成本；叠加每段从满额现金重新建仓（免费重置仓位）。
- **排除项**：非未来函数/数据泄露。label = `Ref($close,-6)/Ref($close,-1)-1`（无前视），成交用 T-1 信号 T 收盘成交（shift=1），train/test 严格时间错开。
- **未修复**（用户要求先不改）：方向是段间持仓跨段传递（真连续账户）或限制"段长必须 > n_days_hold"，另需关注数据源 `$close` 是复权价（如中远海控 2019 显示 0.26 vs 真实 4-5 元）导致目标股数虚高、撞成交量限制（volume_threshold=0.25）只成交 1%-5%。
- **影响文件**：`qlib_engine.py`（_run_rolling）、`periodic_strategy.py`、数据源价格口径。

### 15. ✅ 修复 #14：滚动回测"只买不卖"BUG（持仓跨段传递 + 调仓日全局连续）

- **修复思路（纯外挂，不动 qlib 内核）**：
  1. **持仓跨段传递**：`_run_rolling` 每段结束后用新增 `_extract_end_position(recorder)` 从该段 `positions_normal` 提取段末持仓，转成 qlib account dict（`{"cash": 现金, 股票: {"amount","price"}}`），下一段 `_build_port_config(account=持仓dict)` 传入。qlib 原生 `create_account_instance` 支持 dict 带初始持仓（官方用法），**无需改内核**。这样段首调仓时 `current_stock_list` 非空 → 能卖出不在新 topk 的旧持仓。
  2. **调仓日跨段连续**：`PeriodicTopKStrategy` 新增 `rebalance_base`（回测起点在 qlib 全局交易日历的索引），调仓判定改为 `(全局交易日序号 - rebalance_base) % n_days_hold == 0`，不再用"段内相对 step"。→ 调仓节奏与段长无关，段长 1/2/3/5 天任意都每 n_days_hold 天调仓一次。
  3. **绕开 qlib return 列 BUG**：带初始持仓的账户，qlib `report` 的 `return` 列首日会把"初始持仓市值"误算成收益（实测首日 372%）。`_extract_result` 增加 `initial_account` 参数，改用 `report["account"] / initial_account` 计算段内净值与收益。
- **改动文件**：
  - `backend/app/engine/periodic_strategy.py`：`rebalance_base` 全局调仓日判定
  - `backend/app/engine/qlib_engine.py`：`_run_rolling` 持仓跨段传递（`carry_position`）、`_account_total_value()`、段结果存 `end_position`、`_run_single` 也传 `rebalance_base`
  - `backend/app/engine/metrics.py`：`_extract_end_position()`、`_extract_result(initial_account=...)` 用 account 列算收益
- **验证**（独立临时 workdir，不污染生产）：
  - 周滚动（test_win=1week, n_days_hold=5）：**买入 235、卖出 205**，调仓间隔 7 天（每周一次）；年化从修复前的 2.7e33（return 列爆炸）恢复到 -9.5%（2026 年 1-4 月 csi300 下跌，Linear 周调仓亏损合理）
  - 纯逻辑验证 35 组（段长 1/2/3/5/7/10/21 × n_days_hold 1/2/3/5/10）：段长 ≤ n_days_hold 时调仓日间隔严格 = n_days_hold 且每段内最多 1 次调仓（持仓延续）；段长 > n_days_hold 时段内多次调仓为正常语义
- **影响**：所有滚动回测（single 模式不受影响）收益计算更真实；历史"0 卖出"任务的虚高结果需重新跑才可信。
- **遗留**：数据源 `$close` 为复权价导致的"目标股数虚高撞成交量限制、成交率 1%-5%"问题（#14 中提及）**未处理**，属另一个独立问题。
