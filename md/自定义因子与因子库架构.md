## 0. 现状能力（已落地）

> 本节为**当前已实现**的功能说明（原 `md/因子库特征选择.md` 合并而来，该文件已删除），与下文"2.0 设计蓝图"区分：**本节讲现在能用什么，下文讲未来要建成什么样。**

### 0.1 内置特征集与自定义特征勾选

- **默认特征集**：`Alpha158`（158 个因子）、`Alpha360`（360 个因子，6 字段 × 60 历史）。
- **自定义特征**：前端可**多选勾选**某个特征集里的具体特征（如只选 `KMID`、`ROC5`、`MA20`），回测时仅使用这些特征。
- **全量 / 子集**：不勾选（或勾全）等价于该特征集全量；勾选子集时只计算所选特征。后端用 `SelectedAlpha158` / `SelectedAlpha360` Handler 过滤（`backend/app/factors/handler.py`）。
- 回测请求字段：`feature`（Alpha158/Alpha360）+ `selected_features`（子集列表）。

### 0.2 因子目录接口

| 接口 | 说明 |
|---|---|
| `GET /api/factors/datasets` | 列出所有可用特征集，如 `{"datasets":[{"name":"Alpha158"}],"default":"Alpha158"}` |
| `GET /api/factors/catalog?dataset=Alpha158` | 特征集目录（含 `groups` 分类分组 + `flat` 扁平列表，每条含 name/expression/category/description） |

前端"自定义筛选特征"面板即调用此接口：按分类勾选 / 悬停看公式 / 全选清空。

### 0.3 扩展因子库（Provider + Registry）

新增因子**不需要改接口和前端**（`backend/app/factors/catalog.py`）：

```python
def my_factor_provider():
    return [{"name": "MYF1", "expression": "Ref($close,5)/$close",
             "category": "自研动量", "description": "5日动量因子"}]

FACTOR_PROVIDERS = [
    {"dataset": "Alpha158", "provider": _alpha158_provider},
    {"dataset": "MyFactors", "provider": my_factor_provider},   # ← 新增
]
```

前端 `GET /api/factors/datasets` 会自动返回 `MyFactors`。若新因子集需要自定义处理流程，在 `handler.py` 新增类并支持 `fields` 参数即可。

### 0.4 表达式语法（qlib ops）

因子表达式使用 **qlib 表达式语法**（`qlib/data/ops.py`）：
- 行情字段：`$open` `$high` `$low` `$close` `$volume` `$vwap`
- 时间算子：`Ref($x, n)`、`Mean`、`Std`、`Sum`、`Max`、`Min`、`Rank`、`Quantile`、`IdxMax`、`IdxMin`
- 回归算子：`Slope`（线性斜率，Alpha158 中的 BETA）、`Rsquare`、`Resi`
- 相关算子：`Corr`、`Cov`；逻辑算子：`Greater`、`Less`、`Abs`、`Log`
- **资金流字段（v1.6.5+，现源 moneyflow3）**：`$mf_amount_*`/`$mf_pct_*`（净额万元/净占比%）+ 买卖方向 `_b/_s` + 量（手）`$mf_vol_*`（`tools/dump_moneyflow.py` 生成；金额=万元、占比=%、量=手）
- **资金流方言函数**：`L2_PCT(n[,b|s])` / `L2_AMO(n[,b|s])` / `L2_VOL(n[,b|s])`，n=0 主力 / 1 超大单 / 2 大单 / 3 中单 / 4 小单 → `$mf_pct_*` / `$mf_amount_*` / `$mf_vol_*`；带 `b`/`s` → 买入/卖出方向（如 `L2_VOL(0,b)` = 主力买入量）
- **停牌"删行"算子 `SR`**（v1.6.5，益盟/聚宽语义）：`SR($close)` 按自身 NaN 剔行；`SR($factor,$close)` 按 `$close` 掩码剔行（factor/market_cap 停牌日仍有值需显式掩码）。删除后返回"连续交易日"序列，Ref/窗口不把停牌日当一天；读取向前扩展 250 个交易日跨停牌段

### 0.5 自定义公式因子（已落地，见第 9 章 M1/M2）

益盟/通达信公式 → 翻译成 qlib 表达式 → 进回测。**已实现**：
- `FormulaHandler`（`backend/app/factors/handler.py`，原 SelectedAlpha158/360 保留）
- 接口：`POST /api/factors/translate`、`GET /api/factors/operators`
- 回测字段 `custom_formulas`；前端公式编辑器（整段粘贴 → 实时翻译校验 → 添加/删除/清空）

### 0.6 资金流数据 + L2 方言 + 停牌"删行"语义（v1.6.5 已落地）

- **资金流数据**：东财"资金流向"日频（2016-01-04 ~ 2026-07-28，1055 万行，5,570 只），由 `backend/tools/dump_moneyflow.py` 转成 qlib bin（`mf_amount_*`/`mf_pct_*` 10 字段：主力/超大/大/中/小 五档互斥净额与净占比）。源 h5 在 `E:\rq\moneyflow`，bin 在 `data/cn_data`（gitignore，需单独分发）。
- **L2 方言函数**：`L2_PCT(n[,b|s])` / `L2_AMO(n[,b|s])` / `L2_VOL(n[,b|s])`（n=0..4），与数据档位一一对应。同事复制益盟公式时把 `BIGORDER/ORDERAMT` 组合手改为 L2 写法即可。
  - **（v1.7.1 更新）** 本节初版（v1.6.5）只接入净额、标注"单边买卖/股数档位（`×vol`）不支持"；现源已换 **moneyflow3**（v1.6.8，2013-01-04~2026-08-19，买卖分开），`L2_AMO/L2_PCT` 支持 `b/s` 方向参数，并新增**量字段 `$mf_vol_*`（手）与 `L2_VOL(n[,b|s])`**（v1.7.1）——益盟"×vol 股数/单边买卖"类组合现在可直接翻译。
- **停牌"删行"语义**：qlib bin 区间内停牌日是 NaN 行，与益盟/聚宽"无停牌行"不一致（复牌首日 `Ref=NaN`、窗口被截断）。`CachedQlibDataLoader` 默认对 **feature 组**表达式包 `SR(...)`（label 不包），单因子测试仅因子列包（涨停/停牌判定元数据保持原始），多因子 A158/360/公式/mixed 特征全部按益盟连续交易日语义计算。**语义变更：历史训练/回测结果需重跑**。
- **预热缓冲 `warmup_days`（v1.18.6 已落地）**：`SR` 的静态前扩是 `子ext + LOOKBACK_DAYS(250)`（`ops_ext.py` 的 `get_extended_window_size`），对**固定窗口**算子（`MA`/`REF`/`HHV`…，`_tree_ext_days` 可精确推断）足够；但 `DYN_*` / `BARSCOUNT` / `HHVBARS+Ref` 嵌套这类**动态窗口**的真实所需历史**静态不可推断** → 面板/`D.features` 从 `start_date` 起加载时，评估区间首日因子为 NaN/未收敛。故单因子诊断新增 `warmup_days`（交易日；默认 250、`0`=关闭、env `QLIB_SFT_WARMUP_DAYS`；前端「预热缓冲」输入框）：面板普通组 `read_start = 可推断预热 + wu`、起点敏感组 `精确扩展 + wu`；qlib 回退路径从 `load_start`（按 `D.calendar()` 回退）起 `D.features`；**出口统一裁剪回 `[start_date, end_date]`** —— 预热行不进统计、固定窗口算子结果逐位不变。
  - **注意**：默认 `suspend_remove=True` 时叶子被 `SR(...)` 包裹，`D.features` 本就前读 ≥250 天，故对 `EMA` 这类 ~50 天收敛的算子 `warmup_days` 属冗余（验证预热是否生效需用 `suspend_remove=False` 或动态窗口公式）。

## 1. 设计目标与总体架构

### 1.1 目标

1. **自定义公式因子**：支持粘贴益盟/通达信公式，翻译成可计算的量化因子，喂给回测模型。
2. **因子库**：把常用/自研因子组织起来，可浏览、勾选、入库、管理。
3. **因子评估看板**：对齐聚宽 factorlib，展示因子的 IC / ICIR / 分组收益 / 多空 / 衰减。
4. **因子预处理**：对齐业界标准（去极值 / 标准化，中性化预留），默认专业、可覆盖。
5. **因子值存储**：模式 B 预计算入库，用 h5 高效存储，先定规范后实现。
6. **全程外挂，不动 qlib 内核**：延续项目已有的 `patch_qlib_parallel` / `patch_cancel_train` 外挂模式。

## 2. 核心设计原则（可扩展性）

> 本 2.0 设计最重要的约束：**给后续修改留好空间，别到时候不能改。**

落实为三条架构铁律：

1. **预处理管线必须配置驱动、可插拔**——不能像现状（`handler.py` 里硬编码 `ZScoreNorm`）那样写死在 handler 类里。
2. **因子定义（公式/元数据）与计算逻辑分离**——改公式不改代码，改预处理不改公式。
3. **所有处理步骤做成"处理器链 + 注册表"**——未来加去极值/中性化/新标准化 = 加一个处理器，不动核心。

### 2.1 当前架构的扩展性短板（必须解决）

现状 `backend/app/factors/handler.py`：

```python
class SelectedAlpha158(Alpha158):
    # processors（ZScoreNorm + Fillna）在 Alpha158 基类里写死，无法从外部改
    def __init__(self, fields=None, label_horizon=2, **kwargs):
        ...
```

而 qlib 的 `DatasetH` 是**配置驱动**的（`init_instance_by_config` 传 dict），本可支持 processors 参数，但未暴露。

**结论**：2.0 必须把 handler 改造成"接收 processors 配置"，否则后续加预处理开关会牵一发动全身。

### 2.2 三个扩展接入点

#### 扩展点1：因子定义 = 纯数据（JSON/DB），不写死在代码

```json
{
  "name": "长期线",
  "formula": "A:=MA(-100*(HHV(HIGH,34)-CLOSE)/(HHV(HIGH,34)-LLV(LOW,34)),19); 长期线:A+100",
  "translated_expression": "Add(Mean(...),100)",
  "category": "用户自定义",
  "tags": ["均线", "趋势"],
  "preprocess": { "winsorize": {"method":"mad"}, "normalize":{"method":"zscore"} },
  "eval_periods": [1, 5, 20],
  "status": "draft"
}
```

> 以后改因子、改预处理、加参数，都只是改这条数据，**不动代码**。

#### 扩展点2：处理器注册表（Processor Registry）

```python
PROCESSORS = {
  "winsorize_mad":   WinsorizeMAD,
  "winsorize_quantile": WinsorizeQuantile,
  "winsorize_3sigma": Winsorize3Sigma,
  "normalize_zscore": NormalizeZScore,
  "normalize_rank":  NormalizeRank,
  "normalize_robust": NormalizeRobust,
  "neutralize_market_industry": NeutralizeMktInd,  # 预留
  "neutralize_industry": NeutralizeIndustry,       # 预留
}
```

> 以后新增处理方法 = 往注册表加一个类，**不动调用方**。

#### 扩展点3：预处理配置随请求传入（前端可覆盖）

`BacktestRequest` 增加 `preprocess` 字段（可选）。前端高级选项里能覆盖默认预处理。

## 3. 公式翻译器 FormulaParser（通用解析器）

### 3.1 定位

把粘贴的**益盟/通达信公式文本**，翻译成 **qlib 可计算的表达式**。这是 2.0 的**技术核心**。

### 3.2 处理流水线

```
益盟/通达信公式文本
   │  ① Lexer（词法分析）：token 流（标识符/数字/操作符/函数名/:=/冒号/分号/括号）
   ▼
   │  ② Parser（语法分析）：构建 AST（含 变量赋值 := 、输出线 : 、函数调用、参数）
   ▼
   │  ③ 语义分析：区分"中间变量(:=)"与"输出线(:)"；校验单输出；参数个数/函数名校验；标记外挂算子
   ▼
   │  ④ 变量内联：把中间变量递归展开进输出表达式，形成无变量的单棵表达式树
   ▼
   │  ⑤ 代码生成：表达式树 → qlib 表达式字符串（Mean/Ref/EMA/And/...）
   │     + 有状态算子（FILTER/SMA/...）→ 标记为"外挂算子"特殊节点
   ▼
qlib 可加载的表达式（+ 外挂算子注册）
```

### 3.3 公式输入与输出规则（已确认）

- **公式输入**：前端**整段公式粘贴**进一个文本框。
- **输出规则**：每个公式**只允许 1 个输出因子**（形如 `C:xxxx;`）。
- **中间变量**：用 `A:=...; B:=...;` 定义，翻译器将所有 `:=` 中间变量**内联展开**，只保留最终 `C:` 输出因子。

**示例**（用户提供的益盟公式）：

```
A:=MA(-100*(HHV(HIGH,34)-CLOSE)/(HHV(HIGH,34)-LLV(LOW,34)),19);
B:=-100*(HHV(HIGH,14)-CLOSE)/(HHV(HIGH,14)-LLV(LOW,14));
d:=EMA(-100*(HHV(HIGH,34)-CLOSE)/(HHV(HIGH,34)-LLV(LOW,34)),4);
长期线:A+100;
```

翻译器保留输出线 `长期线` 作为一个因子，`A/B/d` 作为中间变量内联展开。

### 3.3.1 大小写不敏感（重要约束）

**公式关键字大小写不敏感**：用户可能混用 `MA` / `ma` / `Ma`、`HHV` / `hhv`、`REF` / `ref` 等，翻译器必须统一处理，不能因大小写报错。

实现要求：
- **函数名、行情字段、算子关键字**：统一按**大写规范化**后再查找映射表。如 `ma`、`Ma`、`MA` 都规范化成 `MA` 再映射。
- **变量名（`:=` 中间变量）、输出线名**：也**大小写不敏感**——`A:=...` 与 `a:=...` 视为同一变量；输出线 `长期线` 与 `长期线` 视为同一因子（变量名本身也可含中文）。
- **实现位置**：在 **Lexer（词法分析）** 阶段，对标识符 token 统一 `upper()` 规范化（变量名/输出线名除外，因可能含中文且需保留原名做因子名）。
- 规范化后**去重**再查表，避免大小写不同导致重复因子或找不到映射。

> 例：`ma(close,5)` 与 `MA(CLOSE,5)` 解析结果完全一致。

### 3.3.2 赋值符 `:=` 与 `=` 等效

**`A:=...` 与 `A=...` 等效**：益盟/通达信公式中，`:=` 和 `=` 都可用于给中间变量赋值，翻译器必须两种都支持，不能只认 `:=`。

实现要求：
- **赋值上下文**：`变量名:=表达式;` 或 `变量名=表达式;` 都视为**中间变量赋值**，解析结果一致。
- **注意区分 `=` 的两种语义**（依赖上下文）：
  - **赋值**：`A=MA(CLOSE,5);` → 给变量 A 赋值（此时 `=` 是赋值符）。
  - **比较**：`A>B`、`A=B`（用于条件判断，如 `IF(A=B,1,0)`）→ 此时 `=` 是**相等判断**（对应 qlib 的 `Eq`）。
  - **判定规则**：以语句**是否带分号结束/是否用于表达式内部**区分。赋值语句以 `变量名=` 或 `变量名:=` 开头；出现在其他表达式内部的 `=` 视为比较。
- 建议 Parser 阶段统一处理：把 `:=` 和赋值场景的 `=` 都解析成**同一类"赋值节点"**，比较场景的 `=` 解析成"相等节点"。

> 例：`A:=MA(CLOSE,5);` 与 `A=MA(CLOSE,5);` 完全等效；而 `IF(A=B,1,0)` 中的 `=` 是比较。

### 3.4 需覆盖的算子分类（含优先级）

| 分类 | 函数 | 处理方式 | 优先级 |
|---|---|---|---|
| **算术** | `ABS/SQRT/LOG/LN/EXP/POW/MAX/MIN/MOD/INT/CEILING/FLOOR` | → qlib 或组合 | P0 |
| **引用（核心）** | `MA/SMA/EMA/WMA/MEMA/REF/HHV/LLV/SUM/COUNT/FILTER/HHVALL/LLVALL/HHVBARS/LLVBARS/BARSLAST/BARSSINCE/BARSCOUNT/DMA/ALL/ANY/LAST` | → qlib 或外挂 | P0 |
| **行情** | `CLOSE(C)/HIGH(H)/LOW(L)/OPEN(O)/VOL(V)/AMOUNT/TURNOVERRATE` | → `$close/$high/...` 映射 | P0 |
| **逻辑** | `CROSS/IF/IFS/BETWEEN/RANGE/LONGCROSS` | → qlib 组合或外挂 | P0 |
| **统计** | `STD/STDP/VAR/VARP/AVEDEV/SLOPE/FORCAST/DEVSQ` | → qlib 或外挂 | P1 |
| **时间** | `DATE/YEAR/MONTH/DAY/WEEKDAY/BARPOS` | → 需外挂（时间函数） | P2 |

## 5. 因子预处理管线（配置驱动）

### 5.1 处理器链（Processor Chain）

```
原始因子值
   → [Winsorize 去极值]     可选（默认 MAD；可换分位数/3σ）
   → [Normalize 标准化]     必选（整体 ZScore，现有；可扩展 rank/robust）
   → [Neutralize 中性化]    预留开关（默认关，未来可选市值/行业）
   → 已处理因子值
```

### 5.2 如何做到"能改"

qlib 的 `DataHandlerLP` 支持通过 kwargs 传 `processors`。改造方式是：

```python
class FormulaHandler(DataHandlerLP):
    def __init__(self, ..., preprocess: dict = None, **kwargs):
        processors = self._build_processors(preprocess)   # ← 可插拔
        super().__init__(processors=processors, ...)
```

- 加去极值 = `_build_processors` 加一段，或前端多传一个配置。
- 加中性化 = 新增 `NeutralizeProcessor`，注册到 `_build_processors`。
- 改标准化方式 = 换一个 processor 类。
- **全程不动 qlib 内核、不动因子公式、不动回测主流程。**

### 5.3 默认值（对齐研报 + 聚宽）

| 处理 | 默认 | 可配置 | 依据 |
|---|---|---|---|
| 去极值 | **MAD（中位数）** | 分位数/3σ 可换 | 研报"先去极值再 Zscore" |
| 标准化 | **整体 ZScore** | rank/robust 可扩展 | 研报"整体标准化更有利" |
| 中性化 | **关（回测不做）** | 后续留开关可选 | 研报"LGBM 中性化显著降低表现" |

> **注意**：标准化用"整体 ZScore"（拟合区间上整体算均值方差），**不是截面标准化**。现有 qlib 的 `ZScoreNorm` 正是整体标准化，方向正确。

> 本节为**规范设计**，实际 h5 写入在**模式 B（预计算入库）开发时落地**。现在只定接口和目录规范。

`E:\rq\bundle` 实测结构：

### 7.2 因子存储的推荐布局（每因子一文件）

> 因子研究的访问模式是**横截面**（"某一天所有股票因子值"，用于算 IC/分组/训练样本）。若按股票存，算每天横截面要打开所有文件，低效。因此因子存储选"**因子为中心**"。

```
factor_store/                        # 因子数据仓库（模式 B 预计算）
  ├── factors/
  │   ├── <factor_name>.h5           # 每因子一文件
  │   │     - data: (datetime × instrument) 因子值矩阵   ← 轴序：日期在外、股票在内
  │   │     - dates: 日期列表（与 data 第 1 维对齐）
  │   │     - instruments: 股票列表（与 data 第 2 维对齐）
  │   │     - meta(attrs): 公式/参数/预处理配置/版本/ast_hash
  │   ├── <factor_name>_meta.json    # 因子元数据 + 评估结果
  │   └── ...
  └── index.h5                        # 因子索引（可选：所有因子的日期对齐表）
```

**关键设计**：
- 每因子一个 h5 文件 → 加因子 = 新建一个文件，更新 = 只重写该文件，互不影响；**天然并发隔离**（不同因子不共享文件，不会复现 mlflow.db 那种锁竞争）。
- ⚠ **轴序必须是 `(datetime × instrument)`**（**2026-09-11 修订，原稿写反**）。因子研究的主访问是**横截面**（"某一天所有股票的因子值"，用于算 IC / 分组 / 造训练样本），要的是取某一个**行**：
  - C-order 下 `(instrument × datetime)` 取某一天 = 取某一**列** = **跨 stride 访问**；HDF5 未分块时会**退化成整数据集扫描**。
  - 外部实测（5000 股 × 2500 日 × float32 = 50MB）：`(inst,date)` 连续取单日 **151ms** vs `(date,inst)` 连续 **0.4ms**；更刺眼的是前者"读 20 天比读全量还慢 8 倍"（列访问惩罚）。
  - **本仓库实测（2026-09-11，1308 日 × 4841 只 = 24.2MB）**：`(inst,date)` 连续取单日 **3.4~4.0ms** vs `(date,inst)` **0.0ms**；反向（取单股全史）为 `(date,inst)` 3.0~3.5ms vs `(inst,date)` 0.0ms。
  - ⚠ **注意量级**：我们的惩罚只有 ~4ms，远小于外部的 151ms。原因是**跨 stride 的代价随数据规模放大**（24MB 基本能驻留页缓存；50MB / 2500 行时每次列访问要触达更多页）。**结论方向一致，但幅度取决于规模** —— 若将来扩到全历史（2000-2026 共 6455 日 × 6000 只 ≈ 155MB），惩罚会显著恶化，**轴序更必须写对**。
  - **准确表述**：**"轴序在 HDF5 里要命（未分块时），在裸 memmap 里不要命"** —— 裸 `.npy` memmap 两种轴序都很快（~0ms，按页取数、不做 chunk 对齐）；HDF5 则没有"按页读"能力。若坚持 HDF5，可**用 chunk 规避**（如 `chunk=(1日, n_inst)`，实测单日 0.1ms），但 **chunk 形状是零和的**：单日快了，单股全史就慢（实测 286ms）。
  - **结论：`(datetime × instrument)` 连续、不压缩**（HDF5 家族里综合最优：单日 0.4ms / 随机 100 日 2.5ms / 全量 18ms；唯一弱项是单股全史 33ms——因子库极少按股票全史读，看板若要画"某只股票的因子走势"可另存 `(inst,date)` 副本或走缓存，不要为此牺牲主访问模式）。
- **值 vs 元数据分离**：因子值（大矩阵）存 h5；元数据 + 评估指标（IC/ICIR/分组/衰减）存 JSON（量小，看板直接消费）。

**⚠ 存储前提：先决定"存不存 / 存多少"，再选格式**：
- 单因子全历史 float32 ≈ **50MB**（5000 股 × 2500 日）→ 1000 个 = **50GB**，10 万个 = **5TB**。
- 因此**因子值只存"入库 / 活跃子集"（几百~几千个）**；其余只留 **AST + 指标 + 签名向量**，按需重算（当前 `panel_expr` 实时面板求值已足够快，不必人人入库）。元数据是 MB 级，不是瓶颈。
- **格式的优先级低于容量与访问模式**：真正的约束是"存多少"，不是 codec。

### 7.3 为什么选 h5 而非其他格式

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **HDF5（h5py）** | 二进制高效、支持矩阵、增量、**自描述**（attrs 可带轴/单位/版本/ast_hash）、**每因子一文件天然并发隔离** | 需管理文件；**未分块时轴序敏感**（见 §7.2） | ✅ **推荐**（轴序必须 `(date, inst)`，且不压缩） |
| **裸 .npy + memmap** | **最快**（各项 ~0ms，两种轴序都行）、零依赖零 overhead | 无自描述、无校验、**追加新日期要整体重写** | 备选（对"一次算完、很少改历史"可接受） |
| **Parquet** | 列存压缩好、pandas 原生、生态好（DuckDB/BI 可直查） | 长表 `(date,inst,value)` 体积膨胀 ~2.2×、读慢 4~30×；宽表 1.25× | 备选（仅当需要 SQL 直查因子值时） |
| **CSV** | 简单 | 慢、占空间 | ❌ 不适合 |
| **SQLite** | 事务、查询 | 因子矩阵读取不如 h5/Parquet | ❌ **不可当主库**（见 §7.5） |

> **依赖事实（2026-09-11 修订，原稿写反）**：`backend/requirements.txt` 里 **`pyarrow` 是正式依赖**（第 9 行），`h5py` / `tables` 是**注释掉的可选项**（注释写明"接入 rqalpha h5 数据时需要的依赖"）；`requirements_qlib.txt` 里 `h5py==3.16.0` 位于**文件末尾**，注释为"rqalpha h5 数据读取"。
> → 即**用 Parquet 才是"零新增依赖"**；用 HDF5 需确认 h5py 在部署环境可用（开发机已装，但它是随 rqalpha 数据源的可选依赖进来的）。
> **但依赖不该是选型主因**：h5py 装一下就有的东西，按 §7.2 的访问模式选型才对；上面的"推荐 HDF5"理由是**自描述 + 每因子一文件 + 增量友好**，不是依赖。

**压缩（本仓库实测，2026-09-11，`ai_test/bench_factor_store.py`）**：
全 A 前 5000 只 / 2021-01-01~2026-06-01（1308 日 × 4841 只 = 24.2MB）实测：

| 数据分布 | 原始 | h5 + lzf | 压缩比 | 说明 |
|---|---|---|---|---|
| **0/1 稀疏信号**（本仓常见） | 24.2MB | **5.4MB** | **4.48×** | 非零占 46% + 12% NaN |
| 真实价格（15% NaN） | 24.2MB | 21.8MB | 1.11× | 大数值浮点 |
| 日收益率 | 24.2MB | 21.0MB | 1.15× | 小数值浮点 |
| 人造随机浮点（对照） | 24.2MB | 24.2MB | **1.00×** | 复现了外部实测 |

→ **外部"随机浮点不可压"的结论只对随机浮点成立（1.00×，已复现）**；**本仓大量 0/1 因子可压 4.5 倍**，这条实测把外部结论的适用范围钉清楚了。
→ **但压缩有代价**：`chunk=(1日) + lzf` 后单日读仍 0.0ms，而 **250 日读从 4.3ms 涨到 40.8ms（约 9×）**、单股全史从 3.5ms 涨到 34.6ms（约 10×）——**chunk 形状是零和的**（见 §7.2）。
→ **建议**：**0/1 类因子（本仓占比高）压缩值得做**（省 4.5 倍且主访问模式"单日"不受影响）；**连续型因子收益有限（1.1×）不必压**。真要进一步省空间，**量化比换 codec 更有效**。
→ **完整策略见 §7.6**（2026-09-11 与 loop_code 侧交流后定稿）：① 压缩收益**按因子类型分派**（0/1 触发型 4.5~68× / 连续型 1.2~2.3×）；② 存储层**不硬编码类型**，按元数据 `binary_ratio` **自适应开关**；③ **统一杠杆 = uint8 截面分位（256 级）+ gzip = 5.1~5.7×**（保住排序语义）；④ **不把分箱桶号当主存储**（不可逆损失）；⑤ 稀疏仅触发率 <1% 时划算；⑥ **"把行情 bin 全转 h5 提速"是误区**（瓶颈在计算而非格式，真正路径是 M6 因子值预计算入库）。

> 附一条 Parquet 观察：`pq_wide`（inst 行 × date 列）+ zstd 在 **0/1 数据上体积仅 2.1MB**（列式对 0/1 列极友好，优于 h5+lzf 的 5.4MB），但**该形态不适合长历史**（列数 = 交易日数，2500 天 = 2500 列）；`pq_long` 则全面最差（体积 1.95~2.2×、单日读 76~82ms）。

### 7.5 数据库选型（元数据 / 指标 / 血缘）

> **定位（2026-09-11 补充）**：**值走文件**（§7.2），**元数据/指标/血缘走业务库**。
> **前提：将来要上服务器、多人并发写**，所以选型必须按"**多写者**"标准，而不是"单人本地够用"。

**现状核查**：
- **目前没有业务库**。SQLite 仅用于 mlflow 实验追踪（`mlflow.db`）。
- **已经踩过锁的坑**：`backend/app/engine/patches/qlib_parallel.py:115` 注释明确记录 —— 多任务并发写同一个 `mlflow.db` 会触发 SQLite `database is locked`，故改为**按线程独立 db**（`exp_{tid}.db`）绕开。
  → 这条经验直接说明：**SQLite 不能当因子库主库**。将来 FastAPI 多 worker + 后台回测/挖因子任务会**原样重演**该问题。
- **依赖已就位**：`SQLAlchemy 2.0.52`、`alembic 1.19.1`、`pymongo 4.17`、`redis 8.1` 均已安装（见 `requirements_qlib.txt`）。

**结论**：

| 用途 | 选型 | 理由 |
|---|---|---|
| **元数据 / 指标 / 血缘（主库）** | **PostgreSQL** | SQLAlchemy 已是硬依赖、alembic 现成 → 代码侧近乎零成本；**原生支持多写者并发**，是"服务器 + 多人"的正解 |
| 因子值（大矩阵） | **文件**（h5，§7.2） | 数据库不适合存 50MB 级矩阵；且值可重算，不必强一致 |
| 实验追踪 | mlflow（现状） | 保持现状；上服务器后可考虑把 mlflow backend 一并指向 PG（避开 SQLite 锁） |
| 缓存 / 任务队列 / 锁 | Redis（已装） | 现有用途够用，不做主库 |
| MongoDB | ❌ 不用 | pymongo 虽已装，但本场景无文档型需求 |

**本地 → 服务器的迁移策略**：
- 本地开发可先用 **SQLite + WAL 模式 + 单写连接**（单人够用），但**必须把 SQLAlchemy 连接串做成配置项**；服务器换成 PG 时**只改配置 + 跑一次 alembic 迁移，不改业务代码**。
- ⚠ 即便本地用 SQLite，也**不要让多个后台任务直接写同一个 db 文件**（会重演 mlflow 的锁问题）——元数据写入应统一收敛到**一个写入口 / 队列**。
- 建库表（初版建议）：`factor`（因子定义/公式/AST/状态/作者）、`factor_version`（版本 + ast_hash）、`factor_metric`（IC/ICIR/分组/衰减，按持有期与区间）、`factor_value_index`（值文件位置 + 区间 + 行数）、`lineage`（衍生于哪些因子/数据源）。

### 7.6 因子值压缩与量化策略（2026-09-11，与 loop_code 侧交流后定稿）

> **两边的差异必须按"因子类型"分开，不能一句话概括。**

**A. 压缩收益取决于因子分布（双方实测并列）**：

| 因子类型 | 压缩比 | 实测来源 |
|---|---|---|
| **0/1 触发型**（公式因子：CCCMA250 等） | **4.5x ~ 68x** | 本仓 `sig01`（非零 46%）lzf **4.48×**；loop_code 二值因子（触发 8.29%）gzip9 **68.7×** |
| **连续型**（自动挖掘产出） | **1.2 ~ 2.3x** | loop_code 真实因子：lzf 1.21~1.87×、gzip9 1.36~2.33× |
| 人造随机浮点（对照） | **1.00x** | 双方各自复现 |

→ **触发率/非零率越低，压缩越好**：46% 非零 → 4.5×，8.29% 触发 → 68.7×，**二者不矛盾**。**不要拿 68.7× 去承诺所有 0/1 因子。**

**B. 存储层不硬编码因子类型 → 按元数据自适应**：

入库时记录 `dtype` / `nonzero_ratio` / `binary_ratio`（见 §6.3 元数据），写入时据此决定是否开压缩：

- `binary_ratio` 高（稀疏形态）→ **开压缩**（收益 4.5× 起，且单日读不受影响）
- 连续形态 → **不开**（1.2× 收益不值得换 ~9× 读放大）
- **好处**：同时服务两类因子来源（公式因子 / 自动挖掘），**无人需记忆"我这个因子该不该压"**

**C. 真正的省空间杠杆 = 量化，不是换 codec**：

- **首选方案**：**uint8 截面分位（256 级）+ gzip** → **5.1 ~ 5.7×**（loop_code 实测），
  **且保住截面排序语义**（IC / 分组 / 多空近乎无损）—— 因为 IC 是秩相关，**分位等价于排序**。
- 备选：`float16`（整矩阵 2.0×，但损失数值精度、无法还原原始量纲）。
- **对比**：纯 codec（lzf/gzip9）对连续因子只有 1.2~2.3× → **量化的收益高出一倍以上**。

**D. 不要把"分箱桶号"当主存储（重要）**：

- **不可逆的信息损失**：只存 5 档桶号 → **丢掉组内排序** → 无法重算 IC（IC 需完整排序）、无法改分组数、无法做回归/中性化、无法试 "Top30 只" 这类口径。
- **正确区分两个层次**（此处曾出现"层次混淆"）：

| 层次 | 内容 | 说明 |
|---|---|---|
| **评估展示口径** | 分 5 组 / 10 档 / Top10% 多头 | **消费侧参数，与存储无关**；同一份因子值可任意分组、并存成本为零 |
| **存储量化** | uint8 截面分位（256 级） | **保留排序语义**，是"压缩"而非"分箱" |

- 本仓 §6.2 看板写"分 5 组"、loop_code 侧诊断用 `decile_stats(n_grp=10)` —— **两者不冲突**：内部诊断保留 10 档（用于判别"顶档污染"，如 `D1<D2` 提示顶档被污染、宜剔 D1），展示层给 5 组（每组样本翻倍、超额更稳）。**同一份值，随便分。**

**E. 稀疏存储只在触发率极低时划算（反直觉）**：

- loop_code 实测：触发率 **8.29%** 时，**稠密 gzip（0.24MB）比稀疏 `(t,i)` 索引（2.78MB）省 11 倍**。
- 原因：稀疏索引要存**行号+列号两个整数**（≥8 字节/非零位），触发率>1% 时"索引开销 > 稠密压缩后体积"。
- **结论：触发率 < 1% 才考虑稀疏；否则一律稠密 + 量化 + 压缩。**

**F. ⚠ 常见误区澄清：「把行情 bin 全转成 h5 就能提速」—— 不成立**

> 起因：多因子训练 / 单因子测试慢，怀疑是 qlib `.bin` 存储方式导致，"要不要把 bin 全转 h5"。

- **bin 的影响是"文件数多"**（`data/cn_data` 实测 **32 万个 .bin**，每股票每字段一文件 → 取"某字段全 A 每天值"要开几千个文件）。
  **但这条已被治住**：`panel_expr._field_bin_meta`（只 stat 不读，绕开"读全 A 字段要开几千 bin"）+ `_read_field_bin` 进程级 LRU 缓存（v1.17.7，原 20.5s 中 **10.7s≈52%** 的读盘开销可命中免读）。
  实测：CWH 4 万字符 300 只 **20.5s → 2.7s（7.7×）**、CCCMA250 200 只 **9.9s → 1.9s（5.1×）**。
- **转 h5 只能继续压"剩下的读盘"，帮不上"计算"**。而当前的大头是**计算**：巨型公式 4630 个算子节点、`_by_group` 逐段调内核（每段 ~200 行却要 ~10 次 numpy 调用，**调度开销是内核的 6 倍**）、52440 次内核调用/块。
- **另一层错配**：**行情 bin 与"因子值"是两种数据**。
  - **行情原始字段**（`$close/$high/...`）：bin 形态还有**增量更新**优势（新的一天只写一个文件）；转 h5 需整块重写 → **不建议全转**。若真要优化，正解是"**加一个横截面友好的只读副本**（`(date,inst)` h5/npy）与 bin 并存，多字段横截面读走副本、增量更新仍走 bin"。
  - **因子值**（算出来的）：**本来就该存 h5**（§7.2 规范）—— 它是**新产生的派生数据**，不存在"从 bin 转"这回事。
- **真正的提速路径 = M6 模式 B（因子值预计算入库）**：一次算好 → 存 h5（横截面，单日 0.4ms）→ **训练/测试直接读，不再重算**。这才是数量级改善，与"行情格式"无关。
- **结论**：**"训练/测试慢"要按"读盘 / 计算 / 规模"三块拆开定位**；当前瓶颈依次是 **计算 ≫ 读盘 ≫ 规模**，**换行情格式不属于该路径**。

**G. 单因子测试耗时剖面实测（2026-09-11，`ai_test/profile_sft_e2e.py`）**

> 方法：阶段级用 `progress_cb` 打点；桶级复用 `profile_chunk.py` 的插桩（包 `load_field_series`/`parse_expr`/`_panel_dyn`/`_roll`/`_ref`/`_union_index`）。
> ⚠ 关键前提：`QLIB_SFT_PANEL_MAX` 默认 1000，**超过即走 `panel_features_parallel`（子进程）→ 插桩失效**，脚本强制单进程（`MAX=999999`）。
> 口径：csi300 → 459 只 / 2021-01-01~2026-06-01 / h=10。

| 场景 | 端到端 | 特征加载 | **读盘 `load_field_series`** | **`_panel_dyn`** | rest(pandas) | `_union_index` |
|---|---|---|---|---|---|---|
| **CCCMA250**（3.4k 字符） | **10.73s** | 9.30s (86.6%) | 2.36s (**22.0%**) | 2.63s (24.5%) | 3.87s (36.0%) | 0.88s (8.2%) |
| **CUP_POOL**（**279.9k 字符**） | **80.26s** | 78.62s (98.0%) | 2.55s (**3.2%**) | **43.61s (54.3%)** | 29.57s (36.8%) | 1.18s (1.5%) |
| CCCMA250（qlib 回退） | **21.92s** | 20.71s | —（不经 panel_expr） | — | — | — |

**四条实证结论**：

1. **读盘是「常数项」→ 换存储格式没有意义**：公式大 **82 倍**（3.4k→280k 字符），`load_field_series` 只从 **2.358s → 2.550s（+8%）**，占比从 22.0% 掉到 **3.2%**。且这 3.2% 里还含 MultiIndex 构造与 reindex，**纯磁盘 I/O 更小**。→ 本条与 F 节呼应：**"把行情 bin 转 h5"上限就是这几个百分点**。
2. **真正的大头是 `_panel_dyn`（动态算子逐段/全表调度）**：2.63s → **43.61s（54.3%）**，**随公式规模爆炸**。
   - CCCMA250 下 `_panel_dyn` 的 2.630s 中 **ops_ext 内核仅 0.020s（0.8%）→ 99.2% 是 Python 调度**；CUP_POOL 下 666 次调用 / 43.606s = **65.5ms/次**。
   - **代码级根因**（`panel_expr.py` `_by_group` 的 `seg_fn` 分支）：虽已用 v1.18.4 的 `*_vec_seg` 一次性内核，但**每次算子调用仍要做全表级转换与包裹** —— `s.to_numpy()` → `seg_start_arr/seg_end_arr`（每次重建）→ 内核 → `np.asarray + shape 检查 + broadcast_to` → **`pd.Series(out, index=idx)`（重建 59.7 万行）**。666 次 ≈ 3.97 亿行的 Series 构造。
   - **优化方向**：中间结果**统一用 `(arr, idx)` 传递、只在出口包一次 Series**（666 次 → 1 次）；`ss/se` 按 `n` 缓存。
3. **`rest`（pandas 算术/reindex/组装）稳定占 ~36%**（两个场景几乎一致）→ 第二个优化目标。
4. **面板路径比 qlib 回退快 2.0×**（10.73s vs 21.92s），且 **IC / diff 完全一致**（-0.005468 / -0.002988）→ 面板数值等价、性能更优。
   - 另：`parse_expr` 不是瓶颈（280k 字符仅 0.566s / 0.7%）；`reconstruct` 已 0 次调用（v1.18.4 后缓存 key 不再使用）。

**优化优先级（按实测收益）**：① `_panel_dyn` 全表调度（大公式 54.3%）② rest/pandas（36%）③ `_union_index` 缓存（小公式 8.2%，1 次 0.88s）④ `_ref`/`_roll`（9.2%）⑤ ~~读盘~~（大公式仅 3.2%，**最不值得动**）。

### 7.7 单因子测试端到端性能优化：方法学与实测（2026-09-12，v1.18.33~v1.18.36）

#### A. 分阶段耗时基线（同一任务、随版本演进）

**反直觉结论**：起点时以为"大头在切块求值"，实测**切块求值仅占 22%**，真正大头是**统计阶段（95s / 76%）**——其中 `_test_one`（逐因子求值+统计）与**事件研究（0/1 顺带算）各约占三分之一**。

#### B. 可复用测量手法（四条）

1. **端到端分阶段打点**：独立脚本调 `run_single_factor_tests`，`progress_cb` 记录 `(墙钟, 阶段, 百分比)` 时间线 → 得到「解析池 / 特征加载 / 各因子统计段」耗时（`ai_test/profile_sft_allA.py`）。
2. **并行 worker 内部 profile**：worker 是 spawn 子进程、主进程 cProfile 抓不到 → **强制单进程面板**（`QLIB_SFT_PANEL_MAX=999999`）+ cProfile 包住 `_load_feature_panel`；规模取 ~1000 只即可（代码路径与 `_panel_features_chunk` 一致，`ai_test/profile_feature_load.py`）。
3. **单函数热点定位**：patch 目标函数（`enable/disable` 包一层计时）一次跑完拿到各函数墙钟；**切勿嵌套 cProfile**（内层 `enable` 会抢占外层统计 → 数字失真）。
4. **新旧实现对拍（"数值零变化"的唯一证据）**：用 `git show HEAD:<file>` 取旧实现源码 `exec` 进独立命名空间（注入 `__package__`），与当前实现对**同一批输入逐位比较（atol=0）**；随机用例须覆盖 NaN / ±inf / 空输入 / 越界下标 / 大量等值；再端到端比结果字段（0 差异）。脚本：`ai_test/verify_*.py`。

#### C. 四个必踩的坑（已踩）

1. **Windows spawn 与主模块**：进程池 spawn 会**重新导入 `__main__`** → 独立脚本若把主逻辑写在模块顶层（无 `if __name__ == "__main__"` 保护），子进程会再跑一遍并嵌套 spawn，表现为 **worker 起不来、主进程空等（CPU 低、无子进程）**。保护壳 + `sys.path` 注入（`sys.path` 放顶层供子进程复用）。
2. **对拍用例要贴合真实不变量**：`_build_argmax_sparse` 的下标只可能是 `-1` 或合法下标；若用 ±inf 当哨兵会与"NaN 视为缺失"的既有语义不等价（等值取右分支被误触发）→ 改成 **NaN 哨兵 + `av != av`** 才逐位等价。
3. **并行任务墙钟波动 ±10%**：判断 5% 级优化必须用**单进程同口径**（如 `_load_feature_panel` 56.73s → 53.54s）或同进程交替 A/B；粗粒度相减会误导（本次曾出现一次 89s 离群值，重跑即恢复 66s）。

#### 第 3 刀 · 第 1 步：argmax 稀疏表重写（v1.18.39，端到端 −12.5%）

**定位工具（新增）**：`ai_test/probe_dyn.py` —— 包一层 DYN 系列内核，按函数拆出「建表 / 层合并 / 查询」的**调用数、墙钟、元素量、ns/元素**，并记录每次建表的 `n / k / k_max` 与 `lens` 的 `floor(log2)` 直方图。（口径：`CWH_MIX_D_PCT_R40` / csi1000 真实 1980 只 / n=3172661。）

**发现**：同形状（n=3172661、k=7、22.2M 元素）的两次建表 ——

| | 单次 | ns/元素 |
|---|---|---|
| `_build_sparse`（float 极值，一次 `np.fmax` 顺序流） | 110ms | **4.78** |
| `_build_argmax_sparse`（极值下标） | **718ms** | **29.0** |

慢 **6.5×**。主因：每层合并用 `vals_ext[ai + 1]` / `vals_ext[bi + 1]` 取候选值 —— 在 25MB 数组上做**随机 gather**（6 层 × 2 次 × 3.17M ≈ **2.7 亿次随机访问**），外加 ~20 遍逐元素运算。

**三条改法**（先微基准再落地）：

1. **并行维护极值表 `sv`**，候选值改读**连续切片**，去掉 gather；`sv` 只需**相邻两层**（ping-pong 两个 n 长缓冲）。
2. **简化合并**（`_merge_adjacent_vals`）：第 j 层的左右两半是**相邻区间** `[p,p+half)` / `[p+half,p+2half)`，且 `si[j-1][q] ∈ [q, q+2^(j-1)-1] ∪ {-1}`（对 j 归纳，含尾部「沿用 prev」的近似位）⇒ **两半下标只要都有效必有 `ai < bi`** ⇒ 原 `(tie & (bi > ai))` 的 `bi > ai` **恒真**，可删；再与 `b_better` 合并即 `bv >= av`（等值自然取右）。**合并 11 遍 → 6 遍**。
   ⚠ **`_dyn_best_idx_ext` 必须保持原样**：它也用于**查询**路径，而查询的两个候选 `st[js,l1]` / `st[js,l2]`（`l2 = l1 + (lens − 2^js)`）区间**可以重叠**，`bi > ai` 不恒真 —— 简化版只能用在「相邻两半」的建表场景。
3. **下标表降 int32**（n < 2^31 恒成立；返回的下标只被 `i - j` 消费 → 产出 int64）。

**微基准** `ai_test/bench_argmax.py`（五变体交错 A/B，**全部逐位相同**）：28.85 → 13.08 ns/元素（**2.21×**，is_max）｜33.41 → 14.25（**2.34×**，min）。

**A/B** `ai_test/ab_dyn.py`（**子进程** × 3 轮，样本区间不重叠）：墙钟 **26.25 → 22.97s（−12.5%）**｜`_build_argmax_sparse` **4.964 → 1.864s（−62.5%，2.66×）**｜入口累计 `dyn_bars_vec_seg` **8.445 → 4.990s（−40.9%）**。内存峰值 **~250MB → ~160MB**（int64 表 178MB → int32 89MB + 2 个 n 长 float64 缓冲 50MB）—— 512MB 节点缓存的高压场景下，这部分也贡献了墙钟收益。

#### 第 3 刀 · 第 2 步：DYN 窗口几何改「全程原地写」（v1.18.40，几何 1.78×、端到端 ≈ −5.7%）

**定位工具（新增）**：`ai_test/bench_query.py` 逐步计时单次 DYN 查询。

| 步骤 | ms（n=3.17M，k=7） |
|---|---|
| **单次整查询** | **291** |
| 其中「窗口几何」 | **~200**（`_win_lens_vec` 50 + `minimum` 37 + `log2+floor+astype` 51 + `idx-lens+1` 27 + `idx-seg_start+1` 22 + `1<<js` 9） |
| 其中「取表」 | ~136（2 次 gather 99 + `fmin` 37） |

几何**只依赖 `(nvals, seg_start, n)`**，且每个 pass 实测 **3.2 ns/元素** —— 远低于流式带宽 ⇒ **真因是分配**：原实现四行链式表达式逐条各分配一个 n 长临时数组（**11 个 ≈275MB**；整条查询约 17 个 ≈425MB）。

**改法**：抽出 `_dyn_geom(nvals, seg_start, n) -> (js, l1, l2)`，**全程 `out=` 原地写**，只用 5 个缓冲（mask/A/B/C/D）；`np.arange` → `_arange_cached`；`fmin/fmax` 写回第一个 gather（`out=`）。四处入口各缩成 3 行。

⚠ **`maximum(N, 1)` 必须在转 int 之后**（与 `_win_lens_vec` 同序）：`floor(±inf)` 转 int64 得 `INT64_MIN`，若先在浮点上取 max 再转，`INT64_MIN` 会从 `minimum(N, i-seg_start+1)` 漏出来 → 语义错。`np.copyto(C, A, casting="unsafe")` 与 `astype(np.int64)` 是同一 C 转换路径，故逐位一致。

**三个假设被基准证否**（都是先写了基准才否掉的）：
| 假设 | 实测 | 结论 |
|---|---|---|
| `js` 用 `np.frexp` 取指数更快 | 106.9 vs `log2` **31.5** ms | ❌ 更慢（`log2` 是 SIMD 向量化的） |
| `st[js,pos]` 按 `js` 分组后取单层更缓存友好 | **155.6** vs 2D 花式 49.6 ms | ❌ 更慢 3×（逐层布尔掩码开销更大） |
| `np.searchsorted` 求 js 替 `log2` | 57 vs 51 ms | ❌ 更慢 |

**⚠ 方法关键（本步最大的收获）**：本改动只值 ~1s，而大池单进程墙钟跑间抖动 **±18%（≈±4s）** —— **3 轮 A/B 的区间必然重叠，测不出来**（新 22.56/23.91/27.05 vs 旧 21.99/24.66/25.61）。改用**同进程成对测量**（新增 `ai_test/probe_dyn_geom_ab.py`）：patch `_dyn_geom`，每次调用**既跑新实现、也跑旧内联链的复刻**（丢弃结果），并**逐次交替先后顺序**抵消顺序偏差 ⇒ 抖动抵消：

- 16 次调用：新 **1.669s** / 旧 **2.976s** ⇒ **几何 1.78×**（每次比值 1.46~2.21，全部 >1）
- 折算本次 wall 23.11s：**省 1.31s ≈ 5.66%**
- 顺带在**真实数据**上逐位校验 `js/l1/l2`：**0 次不一致**

**⇒ 通用结论**：大池单进程端到端墙钟抖动 ±18%，**凡 ≲5% 的改动都必须用「同进程成对 + 交替顺序」测**（新旧两版都写进探针、在同一份真实数据上各跑一遍），否则会被噪声吞掉。

## 8. Level2 深度分析函数（净额资金流已可用，委托单级留接口）

> **状态（v1.7.1）**：moneyflow3"资金流向"**净额/净占比/量**已接入（见 0.6，公式用 `L2_PCT(n[,b|s])`/`L2_AMO(n[,b|s])`/`L2_VOL(n[,b|s])`）；益盟 `BIGORDER/ORDERAMT` 组合可由用户改写为 L2 写法（净额、单边买卖、`×vol` 量均支持）。真正的 Level2 **委托单/逐笔成交**数据仍未接入，语法层保留、计算层留接口。

### 8.1 数据源层接口（扩展点）

现有 `DataSource.capabilities` 已有能力声明机制，新增能力位：

```python
capabilities = {
    ...,
    "level2_depth": False,   # Level2 深度数据（委托单/逐笔成交），暂无数据
}
```

在 `DataSource` 基类预留抽象方法（有数据源时实现）：

```python
@abc.abstractmethod
def get_level2_depth(self, instrument, start_dt, end_dt) -> List[Level2DepthData]:
    """Level2 深度数据（委托单/逐笔成交）。"""

@abc.abstractmethod
def get_order_flow(self, instrument, start_dt, end_dt) -> List[OrderFlowData]:
    """委托单流/大单统计（Level2）。"""
```

### 8.2 公式翻译器预留

`lexer/parser` **完整实现**这些函数的**语法解析**（识别函数名、参数、构造 AST），在**代码生成阶段**遇到 Level2 函数时返回明确错误：

```
"函数 BIGORDER 需要 Level2 深度数据，当前数据源未提供，暂不可用"
```

这样：**语法层完整支持**（将来有数据直接启用），**计算层留待数据接入**。用户粘贴含 Level2 函数的公式不会崩溃，而是得到清晰提示。

> **v1.7.1 补充**：若公式里 BIGORDER/ORDERAMT 用到资金流组合，改写成数据对齐的方言（n=0主力/1超大/2大/3中/4小）：
> - 净额/净占比：`BIGORDER(1,3)-BIGORDER(2,3)` → `L2_PCT(1)`（超大单净占比）/ `L2_AMO(1)`（超大单净额）
> - 单边买卖：→ `L2_AMO(n,b|s)` / `L2_PCT(n,b|s)`
> - 量（手）：→ `L2_VOL(n[,b|s])`（moneyflow3 源含 `_bq/_sq` 买卖量，v1.7.1 起支持）

### 8.3 前端联动

前端公式编辑器根据 `/api/data-sources` 返回的 `level2_depth` 能力，对 Level2 函数做灰色/不可选提示，并附"暂无数据"说明。

- 自定义公式若输出 **0/1 布尔信号**（如 `冰谷火焰`、`黄金回踩` 这类触发型），在**回归任务（预测连续收益）**下几乎学不动：信号太稀疏（触发频率低、方差极小），IC 接近 0，对 LightGBM 贡献极低，feature_importance 排末位。
- **评估触发型信号要看"按日配对检验"而不是裸的 MWU**：把每天的 `触发组均值 − 未触发组均值` 当做一个日收益序列（约 1170 个点），报告它的均值、t 值和胜率。这比对百万级原始观测做 Mann-Whitney U 检验更有业务意义——MWU 在大样本下 p 值恒趋近 0（界面显示 `0.0000*`）没法看，且同一天内股票收益高度相关、观测不独立会制造假显著；按日配对后样本单位是交易日（近似独立），还能规避触发集中在少数爆发日把收益均值拉高的问题（典型如暴跌抄底类信号：diff 为正、日配对均值却为负）。
- **下一步方向（二选一或都做）**：
  1. **改分类任务**：label 改为多分类（如 涨/跌/平，或 跑赢/跑输 二分类），模型用分类器（LightGBM `objective=multiclass` 等）。稀疏的 0/1 触发信号对"是否上涨"的分类判别力比"涨多少"的回归强。
  2. **增加特征（把稀疏转稠密）**：在公式编辑器里把 0/1 信号改造成连续特征再进模型，例如：触发后强度（触发时的涨幅/强度）、距上次触发天数（`BARSLAST`）、触发热度（近 N 日 `SUM`）、触发后走势（`REF`+`LLV` 组合）。参考：`LLV/HHV/COUNT/BARSLAST/REF/SUM` 都已支持。

## 10. 附录：研报依据

本节结论依据广发金工《机器学习选股训练手册》，是因子预处理设计的实证基础。

### 10.1 中性化：对 ML 回测有害无益

> 原文（研报特征中性化章节）：
> - "对于 **LGBM 模型而言，不管对哪些特征进行中性化处理，都会显著降低所得因子表现。"
> - "对于 GRU 模型而言，特征中性化后虽并未出现因子效果明显下滑，但因子的 IC、收益和回撤表现也并未提升。"

**结论**：因子阶段**不搞中性化**（回测默认不做，后续留开关）。中性化会剔除市值/行业暴露，但 ML 模型自己有能力学习处理，提前中性化等于删除可能有用的信息。

### 10.2 标准化：整体标准化优于截面标准化

> 原文（研报特征预处理章节）：
> - "对特征做**截面处理**会影响对两个模型的学习效果……截面标准化时每天的特征数据都被限定在同样量纲下，不同日期间大小关系被忽视。"
> - "对特征进行**整体标准化**更有利于模型学习时序信息，提升最终因子表现。"
> - "通过首先去极值再进行 Zscore 来规避（极值敏感）这一问题。"

**结论**：
- 用**整体 ZScore**（拟合区间整体算均值方差），**不用截面标准化**。
- 先去极值（MAD）再 ZScore。
- 现有 qlib `ZScoreNorm` 正是整体标准化，方向正确，无需改动。

### 10.3 最终预处理策略

| 处理 | 回测 | 看板 | 依据 |
|---|---|---|---|
| 去极值（MAD） | ✅ 做 | ✅ 做 | 研报"先去极值再 Zscore" |
| 标准化（整体 ZScore） | ✅ 做（现有） | ✅ 做 | 研报"整体标准化更有利" |
| 中性化 | ❌ 默认不做（留开关） | ❌ 默认不做 | 研报"LGBM 中性化显著降低表现" |
| 截面标准化 | ❌ 不用 | ❌ 不用（评估用截面分组算 IC） | 研报"截面处理影响学习效果" |
