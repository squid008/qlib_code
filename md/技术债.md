### 17. `_apply_node` 的"常量首参"防御**根本拦不住** ＋ 左侧标量会把整条公式搞崩

✅ **已清偿（v2.10.69）** —— 见文末「已清偿」表。原记录留一行备查：
12 处 `if s is None` 是死代码（常量为 `float` 非 `None`）＋ `eval` 缓存收尾对 `float` 读 `.index`。

| | |
|---|---|
| **证据**（v2.10.68 探针实测 ✓） | `REF(1, 2)` ⇒ `AttributeError: 'float' object has no attribute 'index'` ✗（**不是** `ValueError("Ref 首参不能是常量")`）｜`FILTER(1, 2)` 同 ✗｜`MAX(1,2)+$close` ⇒ 同样 AttributeError ✗｜而 `$close*(1+2)` **正常** ✓（标量在**右侧**没事 ✓） |
| **根因 ①** | `_apply_node` 里那 **9 处** `if s is None: raise ValueError("… 首参不能是常量")` ✗ —— 但**常量求值后是 `float`，不是 `None`** ✓ ⇒ **9 道防御全是死代码** ✓（这也是它们一直没被覆盖率点亮的原因 ✓） |
| **根因 ②** | 二元算子**左侧是标量**时，`_apply_node` 返回 `float` ✓，而 `PanelEvaluator.eval` 的收尾逻辑假设结果是 `pd.Series` ✓ ⇒ `.index` 崩 ✗（右侧标量走的是另一条分支 ✓ 所以看起来"有时正常"✓） |
| **为什么危险** | ① 用户写 `FILTER(1,5)`（常数信号）**不报错** ✓ ⇒ 回测照跑、结果毫无意义 ✗；② `MAX(1,2)+$close` 这种写法直接 **500** ✓，而它的"对称写法"`$close+MAX(1,2)` 却正常 ✗ ⇒ **极难自查** ✓ |
| **还法** | ① 9 处改判类型：`if not isinstance(s, pd.Series):` ✓（**别**只补 `None` ✗）；② `eval` 收尾加一句"非 Series 直接返回" ✓。⚠ 两处都在**求值热路径**上 ⇒ 必须同时跑 `test_engine_golden`（6 配置 NAV 指纹 ✓）＋ 全部 panel 用例 ✓ |
| **成本** | 改动本身小（约 15 行 ✓），**风险中等**（热路径 ✓）—— 值得**单开一轮**，别和别的改动混在一起 ✓ |
| **状态** | 未动 ✗（本轮探明了、没改 ✓ —— 已删掉跑不通的测试草稿，避免留下误导 ✗） |
